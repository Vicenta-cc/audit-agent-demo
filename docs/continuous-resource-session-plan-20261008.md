# 连续会话资源恢复与能力衔接设计

本次以 `e8fdaef177f1fde5263ae17d974cc928a9157fa4` 为基线，目标是让同一会话在报告前后都能准确操作资源，同时保持任务配置和历史报告不变。设计与矩阵已单独提交为 `cd5c8fb`；随后仅实施阶段 1A 的只读资源目录，结果见验收矩阵末尾。明确选择记录、统一聊天入口和数据库迁移尚未实施。

## 实施边界

- 开发分支：`codex/continuous-resource-design-20261008`。保留原分支及已提交的草案幂等修复，不改其操作身份、事务或迁移逻辑。
- 不部署、不重启线上、不读取或改写生产数据库；验收使用隔离数据。当前没有新增生产备份，后续部署需单独安排一致性备份及恢复演练。
- 不增加一会话多调查，不新增 shell 权限，不重写 System Prompt，不改变 Qwen 正常回答风格。
- 每阶段先落实对应断言，再实现，再验收和独立提交。用错资源、越权、重复写入或历史任务变化，均阻止进入下一阶段。
- 后续入口功能开关默认关闭，由后端控制；客户端只能使用后端告知的能力。关闭新入口不撤销已经成功的业务操作。

## 现有能力及实际缺口

下表路径均相对于仓库根目录，结论来自本地基线代码。

| 业务事实 | 已有存储和入口 | 可复用能力及缺口 |
| --- | --- | --- |
| 临时规则 | `investigation_creation/store.py` 的 `ruleset_proposals`；`resource_edit_history` | 有独立 ID、版本、内容哈希及历史；不能只展示最新一份 |
| 临时词库 | `resource_management/service.py` 的 `lexicon_edits`、`resource_edit_origins`、`resource_edit_history` | 有会话、用户、来源及版本历史；需要统一目录和精确历史版本读取 |
| 保存结果 | 资源库数据库的 `resource_save_receipts`；`get_save` | 有操作 ID、请求哈希、保存结果；保存和编辑不是同一状态，需逐版本关联 |
| 正式资源 | `resource_management/service.py:read`；规则发布版本、词库版本及 snapshot refs | 已有用户权限及版本引用；整个用户资源库应按需分页，不全部加入每轮上下文 |
| 临时词库采用引用 | `resource_management/edit_refs.py` 的 `lexicon_edit_refs` | 引用绑定用户、会话、版本、哈希；当前版本变化会拒绝旧引用，不应改成自动升级 |
| 用户采用规则的依据 | `ruleset_proposal_approvals`；`investigation_creation/approval.py` 的展示及确认核验 | 已有用户消息、展示消息、规则版本和草案修订的关联；展示或保存本身不代表采用 |
| 草案采用配置 | `investigation_draft_revisions` 的版本化配置 | 能读取指定草案修订；不可用编辑稿最新内容替代 |
| 任务实际配置 | `investigation_runs` 的 `draft_revision`、`confirmed_configuration_json` | 有冻结配置；保存任务资源应从服务端定位这个版本，不能让模型重抄内容 |
| 报告 | run 的报告引用、报告运行时快照及授权绑定 | 保留现有专业查询能力、只读快照和权限边界 |
| 会话编辑稿清单 | `resource_management/api.py` 的 GET `resource-edits`；`service.py:list_edits` | HTTP 已有，但返回全量正文且逐项调用 `get_edit`；后者可能创建词库引用，不适合直接当纯只读紧凑目录 |
| Agent 恢复入口 | `resource_management/tools.py` 的按 ID 读取工具；正式资源搜索 | 没有对应全部临时编辑稿清单的 Agent 工具；不知道 ID 时恢复路径不完整 |
| 明确选择的持久化 | 已有采用审批、保存回执、展示记录 | 未发现统一的编辑焦点/显式资源选择记录；不能以最后更新、最后保存或最近展示冒充用户选择 |

目录中的“全部资源”指本会话所有临时候选、关联的正式资源、草案和任务使用的版本。用户其他正式资源通过独立的授权分页查询发现。不能只列采用过的资源，也不能读取其他会话的私有临时稿。

## 阶段 1 资源状态恢复

### 只读目录与精确版本读取

建议新增会话资源投影模块，不再建设一套资源存储。建议接口为 GET `investigation-workspaces/{session_id}/resource-state`，在现有 workspace 授权后读取；阶段 1 不改变聊天路由，也不把新写入能力暴露给报告助手。

目录返回紧凑摘要，正文按需读取。建议结构如下，最终字段在实现前用契约测试固定：

| 字段组 | 内容及依据 |
| --- | --- |
| 资源身份 | `kind`、服务端 ID、用户可读名称、所属会话/正式库、可读写能力 |
| 编辑版本 | 编辑 ID、版本、内容哈希；历史版本可分页读取 |
| 保存版本 | 成功回执指向的编辑版本和正式版本；无回执、查询失败、确实未保存须区分 |
| 草案引用 | 草案 ID、修订、采用资源版本及关联依据 |
| 任务引用 | Run ID、冻结草案修订、冻结配置哈希、资源来源；与当前编辑版本并列显示 |
| 报告引用 | 当前任务授权报告 ID 和版本；保留报告内部会话身份隔离 |
| 明确选择 | 选择目的、精确引用、来源消息/界面事件及确认状态；无证据时为未知 |
| 读取状态 | 分页游标、来源完整性、失效或缺失原因；部分读取失败不能伪装成空目录 |

目录读取必须不创建资源、不发行新引用、不改变版本、不补写历史归属。已有 `get_edit` 的引用发行逻辑继续服务原工具；新投影应复用校验/序列化逻辑，分离其写副作用，不能简单循环调用现有方法。

各数据库内使用一致的读事务；资源库和调查库分开存储，不能声称一次查询获得了跨库原子快照。返回每个对象的实际版本，关键关联不一致时标为待刷新；业务写入仍在现有事务内重新验证预期版本。不得拿目录缓存替代最终权限和版本校验。

分页必须有稳定排序和游标；并发编辑不得使同一分页结果悄悄改变版本。初期可绑定目录快照标识或在变动时要求刷新。具体方案以并发、规模测试结果确定，不能以时间戳单独充当业务版本。

### 保存用户明确选择

优先复用已有采用审批，不修改已冻结配置。若增加通用选择记录，仅增加独立附属表，建议保存：用户、会话、选择事件 ID、用途、资源 ID/版本/哈希、来源用户消息或界面事件、前序选择及时间。

- 用途至少区分“当前编辑对象”“草案采用对象”“查看对象”。保存成功是回执，不能自动成为采用事件。
- 明确界面选择可直接形成事件；自然语言目标由 Agent 提出具体引用，后端验证身份、权限和版本，保留原用户消息依据。不能声称后端能仅凭模型断言证明语言指代正确。
- 有歧义的候选保持未确认，不以最近一个自动写入选择；已有清晰选择不反复询问。
- 选择事件和依赖它的同库状态变更应在一个事务内提交，重放同一事件不重复追加。选择只是指向业务事实，不取代保存回执或审批记录。
- 历史没有选择证据时返回未知，不按排序“补造”。旧会话中无归属证据的资源也不自动分配给当前用户或管理员。

该表的写入接线必须逐个列出调用点并测试；不能仅建空表就宣称实现了选择恢复。阶段 1 可以先完成投影，再验收附属记录，始终保持原聊天入口。

### 编辑版本与任务版本的边界

示例：保存 A；B 编辑到 v3 并用于任务；随后 B 编辑到 v4。

| 用户请求 | 服务端目标 |
| --- | --- |
| 继续修改 B | B 当前编辑稿 v4，携带预期版本校验 |
| 查看任务所用规则 | 任务冻结配置中 B v3 的内容 |
| 保存任务所用规则 | 由 Run 定位冻结草案修订，复用已有任务资源保存路径并校验与冻结内容一致 |
| 保存刚修改好的 B | B v4 的编辑快照 |
| 草案暂不启动，先保存规则 | 保存选定资源；不确认、不启动、不更新任务 |

历史记录可能保存了精确内容但没有完整来源 ID。此时可展示冻结内容并标明来源无法追溯，不靠同名或内容哈希猜测它就是当前某个编辑稿。旧任务缺少结构化词库时沿用明确拒绝保存的边界，不由模型补造。

## 阶段 2 会话和工具衔接

阶段 1 门槛通过后，先接只读能力，再接已有资源写工具；两步分别验收。

- 前端 `InvestigationPage.tsx` 当前因 `reportBinding` 优先进入报告问答；后端 `conversation.py` 还在 PUBLISHED 状态拦截创建助手。两端都要处理，不能只改前端。
- `reportBinding` 保留报告关联职责；任务启动后的配置冻结和一会话一调查约束继续由业务层执行。
- 协调入口按需提供目录、精确读取、现有资源工具及报告查询。报告专业提示、证据查询、数据快照及会话授权仍复用原实现。
- 核验 `adapter.py`、`hermes_m0/plugin.py` 的工具注册、实际可调用集合、延迟工具桥、执行上下文、回执和审计是否一致。不要直接合并工具名列表。
- 报告内部会话 ID 与业务 workspace ID 必须由后端授权关联；不能让模型任意指定 workspace 取得写权限。
- 修复工具调用边界而不是给 shell 开权限。桥工具不得递归调用桥工具；`read_report` 等工具必须按实际注册方式加载和调用。
- System Prompt 只允许必要的工具契约及阶段边界小改动，正常表达风格保留。目录按需读取，不把所有规则正文堆入 System Prompt。
- 功能关闭时走当前路由；功能开启但状态恢复失败时，不执行目标不确定的写入，可继续安全的报告查询或明确说明资源读取失败。

## 重试与兜底

### 必须保留的现状

`backend/hermes_runtime/input_retry.py` 的上限为 **5 次总请求，即初次加 4 次重试**。匹配状态为 400 或未提供状态、错误码为 DataInspectionFailed、消息明确是 input 且不是 output。请求内容保持相同，只重试供应商请求。

当前 creation 模式 Alibaba chat_completions 安装该适配器；资源生成器对 Qwen 使用相同函数并设置 SDK `max_retries=0`。流式降级到非流式共享计数，重复安装不叠加；中断或已输出部分回答时停止重放。耗尽后保留失败。输出拒绝、权限错误、普通网络错误不会被这套输入审核逻辑吞掉。

不能把这套机制泛化成对所有拒绝反复尝试，不能修改请求来规避审核，也不能包裹整个业务轮次。新协调模式若替换 creation 入口，需要明确继承这项行为并测试，不能只因模式名改变而丢失适配器。

### 恢复策略

| 错误/状态 | 处理及验收边界 |
| --- | --- |
| 输入审核拦截 | 保留上述 5 次总请求预算；同一请求跨 SDK、流式降级及协调层不能倍增 |
| 输出审核拒绝 | 保留拒绝路径；查业务回执决定已完成哪些操作，不重新执行成功写入 |
| 模型临时网络错误 | 盘点运行时现有重试后再确定单一预算、退避和取消；不能另加一层包整轮的重试 |
| 参数错误 | 仅在校验明确未写入时允许纠正，限定次数；不循环猜资源身份 |
| 资源版本过期 | 重新读取并核对实际内容；内容已变或用户意图不明时重新确认，不静默采用最新版本 |
| 已提交但模型回答失败 | 读取已验证的操作回执，向用户准确报告成功对象和版本；不重放保存 |
| 明确未写入 | 在原操作的合法恢复路径中纠正重试；草案沿用 e8fdaef 的判断，不扩大可重试错误名单 |
| 写入状态未知/处理中 | 先查询原操作；不能凭超时、新 operation ID 或模型猜测判断未写入 |
| 权限不足 | 不重试写入，不泄露其他用户资源 |
| 目录/报告读取失败 | 不声称已参考内容，不编造结果；已成功写入的其他操作仍按回执报告 |

当前 `conversation.py` 在失败轮次中针对已验证的 draft/run 检查点生成恢复答复，但不能据此认定所有词库/规则保存已具备同等兜底。阶段 2 需补资源回执与降级答复的接线，并测试“一轮保存 A 成功、保存 B 失败、最终模型回答失败”的逐项结果。正常回答仍由 Qwen 自然生成，固定文案仅用于异常兜底。

恢复日志记录用户作用域、workspace/turn/operation/attempt、工具、精确目标版本、write_status 和供应商 request ID；不把密钥或完整敏感内容写入普通日志。区分模型请求重试次数和业务执行次数。

## 阶段门槛

1. 阶段 0：核实基线、测试命令差异、隔离数据路径；保存当前回归结果。没有给线上创建备份，不把本轮说成部署准备已全部完成。
2. 阶段 1：A/B、各版本、保存回执、选择依据、草案/任务关联能在新进程无模型历史时恢复；零读取副作用；权限/并发/旧库测试通过。
3. 阶段 2：先完成“问报告→读另一套规则→再问报告”，然后验证资源写入与回执兜底；开关关闭回归通过；任务和报告快照不变。
4. 阶段 3：真实 Qwen 多轮、浏览器刷新/SSE恢复和故障注入完成；检查工具轨迹及落库事实。不得把假模型测试或服务层 HTTP 200 计为真实对话通过。
