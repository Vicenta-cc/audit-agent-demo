# 新 M3 多流程与响应时间验收（2026-09-11）

本轮按真实多轮自然语言对话验证资源管理和任务创建，发现并修正两个产品流程问题。8 类场景分别完成验收，成功记录共 22 轮对话、5 个确认 Run 及对应执行 Job。场景经历修复和定向复验，不将早期失败改写为一次全绿运行。

## 隔离和测试边界

- 仅修改 `xhs-audit-agent-m3-resource-lifecycle-experiment` worktree，分支 `codex/m3-resource-lifecycle-experiment`；没有合并、部署或操作 K2 服务。
- 真实模型为 qwen3.7-plus，thinking 开启，使用用户独立提供的 Token Plan 地址与凭据。凭据仅经无回显输入及进程内存传递，不进入仓库或证据。
- 数据为一次性 SQLite，包含应用默认资源和专门的合成招聘诈骗规则/词库；没有修改用户正在使用的正式资源库。
- 使用真实业务工具、保存事务、Draft 确认、Run 入队和执行 Job 编译。没有运行 worker、真实平台抓取、账号登录或实际审核/报告生产。

## 场景结果

| 场景 | 结果 | 核实内容 |
| --- | --- | --- |
| 读取已有 rule 与 lexicon | 通过 | 两轮只读；不建立编辑副本，不写正式资源，不建任务；区分主词、变体、标签和禁用词 |
| 修改已有 rule 与 lexicon | 修正后通过 | 改主词并保留变体/禁用/标签；改规则命中条件；先改会话副本，正式库不变；保存后分别增版，再从后台重新读取核对 |
| 用已有 rule 与 lexicon 发起任务 | 通过 | 正式规则＋正式词库；先 Draft，明确确认后一个 Run/Job；只搜索启用主词 |
| 创建新 rule 与 lexicon、保存并发起任务 | 通过 | 两类资源真实创建并分别保存；后续 Draft 使用正式版本，确认后创建 Run/Job |
| 没有合适资源，询问后创建并发起 | 通过 | 查库无合适资源后询问；用户拒绝则停止；后来同意才创建；两类资源均临时使用；展示、采用、确认后才创建 Run/Job |
| 正式 rule＋临时 lexicon | 通过 | 单独生成词库，不保存；主词与变体分离；正式规则配临时搜索词确认执行 |
| 临时 rule＋正式 lexicon | 修正后通过 | 单独生成并展示规则；后续采用精确 Proposal 和正式词库；正确绑定搜索指纹并确认执行 |
| 普通调查请求自行发现资源缺口 | 通过 | 用户仅要求发起天文器材销售误导调查，系统自行查库并询问是否生成，没有擅自生成、建 Draft 或启动 |

所有成功启动场景均校验搜索词、Job 编译和重复编译不重复建 Job，并验证已确认 Draft 不可修改。实际抓取效果不在本轮结论内。

机器汇总：`docs/evidence/m3-resource-lifecycle/flow-matrix-summary-20260911.json`，逐场景列明证据文件与成功轮次，不隐藏修复前失败。

## 发现并修正的问题

1. **“先修改展示、不保存”只返回文字方案。** 首次模型读取后展示了拟修改内容，却未真正建立编辑副本。补充工具指导，明确“不保存”指不写回正式库；实际修改须建立并更新会话副本，不能再要求用户批准已经请求的修改。复验确认副本已改、正式库未改，之后能保存回原处。
2. **词库完整内容指纹被当作任务搜索指纹。** 完整内容包括变体、标签和编辑元数据，任务仅绑定启用主词。模型误用完整指纹导致采用失败及无效重试。正式词库读取现在直接返回 `runtime_content_hash` 和可用于 Draft 的 `recall_plan`；读取使用同一 SQLite 读事务。提示明确两个指纹不可混用，词库配置错误不能靠修改已展示规则绕过。原版本、指纹和采用校验未放宽。

新增回归确认：只改变体会更新完整资源版本，但任务搜索配置保持相同；读取返回的正式词库配置可直接与已展示的临时规则绑定。资源生命周期、规则采用、确认与执行回归共 **132 项通过，12.77 秒**。

另校正了验收脚本自身的两个断言：已确认 Draft 异常继承通用错误码，必须判断异常类型；询问措辞包括“请问你希望”，不能用过窄的词表误判没有询问。对应早期记录保留为失败/中止，并在后续场景复验，未计作产品故障。

## 响应时间测量方式

功能场景每轮记录从接受请求到完成回答的后端耗时、provider 调用次数和业务工具函数耗时。新旧对照用原基线 `cad3eabd583543fac27a45f211122e2ca924ed2b` 的只读导出与修复后的实验代码，各自启动独立进程、会话和数据库。

两类请求完全相同：一类使用已有赌博规则/词库准备 Draft；另一类单独生成 3 条招聘押金诈骗规则。每类 3 组，交替旧→新、新→旧、旧→新，串行使用同一模型、thinking 设置、付费接口与输出上限。功能验收与性能对照不同时占用接口。

统计完成整轮回答耗时，不包含浏览器传输及渲染。保留全部样本和模型缓存 token 统计；没有强制清空服务端缓存。3 个样本只用于观察，不作为 p95 或统计稳定性保证。首个模型流片段可能是思考或工具参数，不将其当作用户可见首字。

### 性能结果

12 次测量均已返回。新版实际操作完成 6/6，旧版完成 4/6。旧版有一次仅描述配置而没有创建 Draft，一次仅输出规则文字而没有创建 Proposal；这两次保留为未完成，不把它们当作速度优势。

以下仅比较同组中**双方都完成实际操作**的样本，每类 2 组有效配对：

| 相同操作 | 原基线中位数 | 新版中位数 | 观察到的变化 |
| --- | ---: | ---: | ---: |
| 使用已有资源创建 Draft | 34.955 秒 | 37.477 秒 | +2.522 秒，+7.2% |
| 生成 3 条可采用的临时规则 | 63.786 秒 | 72.895 秒 | +9.110 秒，+14.3% |

本轮观察到新版整轮响应略慢，规则生成增加更明显；样本少、生成长度和模型耗时波动大，不能将这两个比例解释为稳定性能退化幅度。所有成功样本的非配对中位数也在 JSON 中保留：旧/新 Draft 为 34.955/37.721 秒，规则生成为 63.786/80.864 秒；两边成功样本数不同，主表采用配对统计。

原始样本（括号注明未完成实际操作）：

| 请求 | 配对序号 | 旧版秒数 | 新版秒数 |
| --- | ---: | ---: | ---: |

对照中业务工具函数累计耗时最多约 0.057 秒/轮，主要等待发生在模型调用侧。新版工具由 10 个增至 17 个，首个 provider 请求的提示 token 在已有资源场景约由 5,790 增至 7,215；生成 token 数及调用次数也有变化。本轮没有单独控制这些因素，不能把延迟变化全部归因于某一个因素。

新增完整流程的实际等待也应单独看：只读约 14 秒；修改两类资源约 32 秒；保存两类资源约 17 秒；现场生成并保存规则和词库约 87 秒；明确确认启动约 11–14 秒。这些是功能场景单次观察值，不是它们的长期分位数。

完整性能证据：`docs/evidence/m3-resource-lifecycle/qwen-latency-comparison-20260911.json`。

## 复现

在实验 worktree 中使用已安装依赖的 Python：

```sh
python scripts/resource_experiment.py tests/test_resource_lifecycle.py tests/test_ruleset_proposal_approval.py tests/test_temporary_ruleset_execution.py
python scripts/resource_qwen_acceptance.py --base-url YOUR_AUTHORIZED_BASE_URL --flow-matrix --token-budget 2500000 --max-calls 150 --output qwen-flow-matrix-repeat.json
python scripts/resource_latency_comparison.py --base-url YOUR_AUTHORIZED_BASE_URL --pairs 3 --output qwen-latency-repeat.json
```

真实模型命令会提示无回显输入 Key。可用多次 `--scenario` 选择定向复验；名称见场景汇总 JSON。验收失败时脚本返回非零状态。
